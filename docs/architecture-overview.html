Weaver-Next 架构与技术设计总览

Weaver-Next 是一个本地优先的语义画布 / 知识图谱系统，以插件形态运行在 AI 编码代理宿主（OpenAI Codex 与 Claude Code）内。每个项目一张内容图（content graph），被投影为多个独立视图；Agent 只能通过可审计的 ChangeSet 修改图内容，用户在 React 白板上预览并批准。所有数据持久化在项目本地的 SQLite。

TypeScript · ESMnpm workspacesReact 18 + React FlowMCP (stdio)SQLite (node:sqlite)esbuild + Vite 7Zod contractselkjs / d3-force

系统概览#

整个系统由三层组成，围绕一个核心原则设计：内容与呈现分离、意图与结果分离、Agent 与数据分离。

  • 宿主层 —— Codex / Claude Code 通过 stdio 启动 MCP 服务器；Codex 内嵌 ui:// 原生面板，Claude Code 打开带 token 的回环浏览器预览。两个宿主最终都走同一条回环数据链路。
  • 服务层 —— @weaver/mcp 暴露整合后的工具面（consolidated dispatcher tools），同时内置一个 loopback HTTP/SSE Hub，承担 widget 静态资源、/mcp-rpc 进程内分发、/events 事件流。
  • 数据层 —— @weaver/storage 用 Node 内置 node:sqlite 落盘到 <workspace>/.weaver/weaver.sqlite（WAL 模式），资产以 sha256 寻址存磁盘。
💡
Info · 设计基线

每个 Weaver 功能都必须同时在 Codex 与 Claude 两个宿主中可用，两者仅入口不同——这是贯穿所有模块的第一约束。

Monorepo 布局#

使用 npm workspaces（"workspaces": ["apps/*","packages/*"]），共享 tsconfig.base.json（ES2022 / NodeNext / strict），Biome 做 lint/format，Vitest 做测试。

包路径职责
@weaver/contractspackages/contracts全领域 Zod schema + 推导类型，唯一事实源；仅依赖 zod
@weaver/corepackages/core纯领域逻辑：applyGraphOperations、applyLayoutOperations、diffLayoutDocuments、resolveSceneContext
@weaver/scene-packspackages/scene-packs13 套内置 ScenePack（按思考领域的节点/边类型词表）
@weaver/visual-templatespackages/visual-templates17 个不可变 VisualTemplate + 场景角色绑定 + 校验
@weaver/layout-enginepackages/layout-engine确定性布局候选生成；依赖 d3-force、elkjs；子入口 ./semantic
@weaver/storagepackages/storageSQLite 持久化（node:sqlite）、资产存储（sharp）、迁移、事件日志
@weaver/mcppackages/mcpMCP 服务器 + 回环 HTTP/SSE Hub + widget 分发
@weaver/widgetapps/widgetReact 18 画布 UI，Vite 7 构建为单文件

构建顺序（根 build:packages）：contracts → core → layout-engine → scene-packs → visual-templates → storage → mcp → build:widget → build:plugin / build:release。其余顶层目录：plugins/（发布快照）、scripts/（构建发布）、skills/（Agent 技能剧本）、.codex-plugin/（插件清单）、.weaver/（运行时工作区数据）。

核心领域模型#

全部定义在 packages/contracts/src/（space.ts、visual.ts、layout.ts、actions.ts、widget.ts、failure.ts）。

Figure 2 · 领域模型与实体关系

内容图：Project / Node / Edge / Asset

  • SpaceProject —— id、title、goal、scenePackId/Version、automationLevel（cautious / collaborative / automatic）、defaultViewId，以及两个乐观并发计数器 graphRevision 与 viewCatalogRevision。
  • SpaceNode —— content 是以 kind 判别的联合：document（markdown + 封面 + 内嵌资产）、image（assetId）、link（url + enrichment 状态）、chart（line/bar/pie/area/metric + series + sourceNote/asOf 审计字段）。schema transform 强制 contentKind === content.kind。
  • SpaceEdge —— 有类型、有方向；applyGraphOperations 拒绝自环（SELF_EDGE）与跨项目边（CROSS_PROJECT_EDGE）。
  • Asset —— 仅图片、≤20MB、sha256 寻址，含 storageUri + thumbnailUri。

视图与投影：一图多视

  • ProjectView —— viewType ∈ canvas / tree / graph / board / timeline / flow / table；生命周期 active / trashed（含 purgeAfter）、置顶排序、createdBy（user / agent / template）。
  • ProjectionSpec —— 判别式联合，描述同一张图如何投影到各视图族（tree 的 rootNodeType/parentEdgeTypes、board 的 columnField、matrix 的 x/y 象限、timeline 的 timeField、table 的 columns…）。
  • VisualTemplate —— 不可变、带版本的蓝图：family / renderer / starterBlueprint（≤20 节点角色）/ sceneBindings / projection / layoutPreset / theme / agentGuidance。硬性不变量：把模板应用到既有项目绝不改动图内容，只新增视图与布局。

ChangeSet：唯一变更通道

ts
// packages/contracts/src/layout.ts — 图的唯一变更路径
type ChangeSet = {
  id: string; taskId: string; projectId: string;

Warn · 并发守卫

Apply 时校验 baseGraphRevision / baseLayoutRevisions，版本冲突则将任务置为 stale；同时自动放置新节点、清退未触碰的模板占位（starter）节点。Agent 从不直接接触 SQLite 或 .weaver 文件。

MCP Server 架构#

入口 packages/mcp/src/server.ts → createWeaverServer()（create-server.ts）。面向 Agent 的传输是 stdio（StdioServerTransport），并带完善的宿主死亡检测（stdin EOF、stdout EPIPE、未捕获 EPIPE → 自我终止），防止宿主重启后遗留孤儿进程。

整合分发器（consolidated dispatcher）

源码注册的是少量整合工具，用 resource / action 判别字段扇出到 ~80 个细粒度操作，而非平铺 80 个工具：

整合工具扇出目标（节选）
weaver_read_sessionbound_canvas · task · canvas_tasks · canvas_context · canvas_view_state · resolved_context · guard
weaver_read_catalogproject.list · view.list/search/get · template.list/get/validate/preview · artifact.get · asset.metadata/preview
weaver_canvas_actionclaim · sync · switch · create_node · update_node · archive_node · attach_asset · enrich_link · layout_operations · revert_layout
weaver_task_action / weaver_review_action / weaver_catalog_action任务状态机动作 / 审批动作 / 目录变更动作
独立工具weaver_open_space · weaver_prepare_task · weaver_submit_changeset · weaver_recommend_layout · weaver_import_asset · weaver_get_diagnostics · weaver_read_graph · weaver_subscribe_canvas

动机：Codex 会丢弃过大的工具 schema。weaver_submit_changeset 甚至对外宣告宽松的 z.unknown() 输入（内部再严格校验）以免被剔除；create-server.ts 维护 CRITICAL_MODEL_TOOLS 清单并用 computeToolSurface() 诊断宿主是否静默丢工具。

createWeaverServer 对 server.registerTool 做了包装：把每个工具的 Zod shape + handler + _meta 收进 registry Map（供回环 /mcp-rpc 进程内分发）、注入结构化计时日志、给预览白名单工具自动打 openai/widgetAccessible 标记。

会话身份收敛

session-identity.ts 从启动 cwd 确定性派生 chatSessionKey（syntheticChatSessionKey），使 stdio Agent、兄弟 MCP 进程、浏览器 widget 收敛到同一个画布绑定。宿主类型由启动脚本注入 WEAVER_HOST_KIND（start-mcp.mjs=codex，start-mcp-claude.mjs=claude）。

Widget / UI 架构#

apps/widget：React 18 + @xyflow/react（React Flow）画布，Vite 构建（base:"./"，inlineDynamicImports，单文件产物）。src/main.tsx 把状态提升到根组件，穿引一组领域 hooks：useProjectBootstrap、useCanvasBindingSync、useCanvasGraph、useCanvasEventStream、useViewCatalog、useVisualTemplateGallery、useDisplayMode 等；渲染核心在 components/CanvasStage.tsx，配套 ChangeSetPreviewPanel、LayoutCandidatePanel、TemplateGalleryModal、DocumentEditorPanel、ViewLibraryDrawer。

三段式传输选择（mcp-client.ts）

ts

if (claudePreview)  // POST {rpcPath:/mcp-rpc} + x-weaver-preview-token（由 /preview 注入 window.__weaverPreview）
else if (codexEmbedded) {
  // 1st: 回环 /mcp-rpc（window.__weaverCodexLoopback，绕开 Codex tools/call 代理的 -32000）
  // 2nd: Apps-SDK App.callServerTool 代理（mcp-app-connection.ts，管理 connect/reset/drain）
}
else // dev: POST /api/mcp（Vite proxy）

packages/mcp/src/widget.ts 用内容哈希生成 buildId，产出两种 HTML 变体：inlineWidgetHtml（CSS/JS 全内联，供 Codex 原生面板）与 bundledWidgetHtml（资产由回环源提供，供浏览器预览）；resources.ts 同时注册一个稳定的 LEGACY_WIDGET_URI，防止 Codex 缓存的描述符过期。display_mode 支持 inline（聊天内 InlineEntryCard 预览卡）与 fullscreen（完整白板）。

存储与持久化#

无外部数据库。workspace-store.ts 的 WorkspaceStore 打开工作区、跑迁移，并暴露命名空间外观：sessions / catalog / graphChanges / layoutReviews / assets / tasks / artifacts。行以 JSON data 列存储，读取时再过一遍 Zod schema（双保险校验）。

text
<workspace>/.weaver/
├── weaver.sqlite            # WAL · foreign_keys=ON · CURRENT_SCHEMA_VERSION = 7
│   ├── project / node / edge
│   ├── layout / layout_history / layout_run
│   ├── project_view / canvas_view_state / canvas_session / chat_canvas_binding
│   ├── agent_task / changeset / artifact / asset
│   └── project_event        # 自增序列事件日志（SSE 回放源）
├── assets/{original,thumbnails,tasks}/
└── exports/
🛑
Danger · 迁移策略

prepareWorkspaceData 检测到 schema 版本不匹配时，会把整个 .weaver 目录重命名为带时间戳的备份（.weaver-backup-…）而非就地迁移——保守但不可逆地保留旧数据。

布局引擎#

generateLayoutCandidates(input)（engine.ts）产出确定性、有种子的候选：seededRandom 由 projectId:viewId:layoutRunId:index 哈希派生，同输入必得同布局。Agent 只书写 LayoutPlan（语义意图）——scope / strategy / constraints（pin·align·rank·group·emphasis）/ preserve（pinnedNodes、mentalMapWeight）——从不书写坐标。

策略实现适用
layered / tree / timeline / swimlaneelkjs（layered）有向层级结构
forced3-force无明显层级的关系图
radial / grid自研（radial 尊重 emphasis 约束为中心）中心辐射 / 规整排布
cluster / hybridsrc/semantic/：detect（分簇）→ size（枢纽更大）→ micro（簇内）→ macro（簇间 pack + gutter）语义聚类画布
Figure 6 · 布局推荐流水线（Agent 写意图 → 引擎出候选 → 用户定结果）

候选由 scoreLayout（score.ts）打分，权重来自 ScenePack 的 scoringWeights；指标含 overlap、edgeCrossings、displacement、compactness、clusterSeparation、directionFlow、hardViolations。钉住的节点会被 restorePinned 还原；边按簇感知路由（簇内 bezier、跨簇正交）。运行生命周期：weaver_recommend_layout 校验 revision → 生成候选 → 存 layout_run（status=preview）→ 任务进入 pending_review → 用户 apply / revert；layout_history 保留历史版本供回滚。新视图满足条件（canvas/graph、≥4 节点、≥1 边）时用 seedSemanticLayout 自动播种。

Agent 任务系统#

存储在 packages/storage/src/agent-tasks.ts，工具在 packages/mcp/src/tools/agent-tasks.ts，配套技能剧本 skills/weaver-develop-space、weaver-layout-space、weaver-watch、weaver-review-changes。

Figure 5 · AgentTask 状态机（虚线 = 异常路径）
Prepare

prepareAgentTask(FromBoundCanvas) 把实时 CanvasContextSnapshot（选区、锚点、pinned context、expectedGraphRevision）快照进任务；要求画布在线、可代理、租约有效；已有活动任务则拒绝（ACTIVE_CANVAS_TASK_EXISTS）。

Dispatch

confirmAgentDispatch（幂等 dispatchKey）；未确认/拒绝走 failAgentDispatch。

Start + 读取上下文

weaver_task_action(action:"start") → running；Agent 读 manifest 与 resolved_context（resolveSceneContext 按场景策略裁剪的邻域）。

Heartbeat

reportTaskProgress 递增 taskRevision，驱动画布 busy pill 并重置空闲收割计时。

Submit → Review

weaver_submit_changeset 置 pending_review；用户在画布 apply / reject。develop_then_layout 意图下 apply 后进入 ready_to_continue（activeStage=layout），Agent 以 continue（守卫 expectedTaskRevision）接续并推荐布局。

收割（reaping）：reapExpiredCanvasTasks 懒式清理沉默任务——prepared >120s、dispatched >180s、running 空闲 >600s，外加 30 分钟硬性生命周期上限（心跳但卡死的 Agent 也无法霸占画布）；pending_review / ready_to_continue 等待用户、永不收割。Watch 模式：用户在画布 composer 输入指令，Agent 长轮询 weaver_await_canvas_prompt 领取为 dispatched 任务。事件流：event-hub.ts 签发 token 门控的 SSE grant，widget 以 Last-Event-ID 断点续传回放 project_event（SQLite 尾随 + fs.watch）。

  • Widget —— vite build → 单文件 apps/widget/dist/index.html（相对 ./ 引用）。

关键架构决策#

ADR-01
ChangeSet 是唯一变更通道

所有图 / 布局写入都是带 revision 守卫、可审计、须审批的 ChangeSet；Agent 从不直接落盘。冲突即 stale，apply 附带自动放置与占位清退。

ADR-02
Contracts-first / Zod 全覆盖

一套 @weaver/contracts schema 定义并在读写两端复验所有实体；@weaver/core 保持纯函数、可独立测试。

ADR-03
内容与呈现分离

一张不可变语义图 → 多个 ProjectView（经 ProjectionSpec 投影）；VisualTemplate 不可变且内容保持；几何独立存于 LayoutDocument 并有自己的 revision。

ADR-04
Agent 书写意图而非结果

LayoutPlan（约束/策略）而非坐标、asset id 而非路径、真实模板 id 而非杜撰。布局确定性有种子，候选可复现。

ADR-05
整合分发器工具面

~80 个细粒度操作折叠为 ~13 个 resource/action 工具以适配 Codex 的 schema 上限；CRITICAL_MODEL_TOOLS + 诊断工具侦测宿主静默丢工具。

ADR-06
一条回环链路服务两个宿主

单个 token 门控 SseEventHub 承担 widget 资产、/mcp-rpc、/api/bootstrap、/preview、/events；端口 + token 由 cwd 派生，进程更迭 URL 不变（leader/follower 重绑）。

ADR-07
会话身份确定性收敛

同一宿主启动下所有进程从 cwd 派生同一 chatSessionKey，绑定同一画布；租约模型（bindingRevision / leaseId）支持离线心跳接管。

ADR-08
技能作剧本、工具作执法

skills/*/SKILL.md 是自然语言操作手册，编排 MCP 工具；所有不变量在服务端强制，剧本无法绕过守卫。

ADR-09
韧性优先的运维设计

宿主死亡自检自杀、懒式任务收割 + 硬性寿命上限、schema 不匹配整目录备份、内容哈希 buildId 防陈旧缓存、逐调用结构化日志。
